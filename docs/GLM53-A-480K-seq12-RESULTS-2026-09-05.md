# GLM NVFP4 (a) experiment — 480K ctx / seq12 — Results (2026-09-05)

## Question
Does right-sizing the window (1M->480K) + cutting seq (64->12) improve 3-4 agent @400K decode / per-turn latency?

## Config (verified live)
- 1M/seq64 (baseline, prior): CONTEXT_LENGTH=1048576, max-num-seqs 64
- 480K/seq12 (tested): CONTEXT_LENGTH=491520, max-num-seqs 12
- Both: gmu 0.68, mnbt 16384, fp8 KV 24GiB/rank (pool 3,420,465 tok), block 2304, DFlash2 k=7, marlin, chunked-prefill on (thr 2048), graphs FULL_AND_PIECEWISE.
- NVFP4 RedHat compressed-tensors, sm121-v12-dflash2-topkfix image.

## Growing-context C1 probe (single agent, +30K/turn, thinking low) — 480K/seq12
| ctx | wall/turn |
|---|---|
| 32K-256K | 2.9-6.3s (FASTER than 1M baseline ~9s) |
| 288K+ | 22-31s persistent stall (1M baseline stayed ~9s) |

## Growing-context C3 probe (3 agents) — 480K/seq12 (intermittent contamination noted)
- Some turns 3-13s; turns 6-8 (192-256K) spiked 67-95s wall; agent1 repeatedly slow.
- Engine gen throughput dropped to 0.3-6 tok/s during stalls even at 2-3 concurrent reqs.

## Memory math (answers "would raising seq OOM?")
- Pool 1865 blocks / 3.42M tok, max_concurrency 6.96 @ full 480K window.
- 3 agents x full 491K window = 642 blocks = 34% of pool. 3-4 x 400K = 28-37%.
- => NO OOM risk raising seq. Pool has ~3x headroom. seq12 is not protecting memory.

## Conclusion
- 480K genuinely helps decode below ~288K (~3x faster than 1M at low-mid ctx).
- BUT a reproducible decode STALL emerges past ~288K ctx (decode->0-0.6 tok/s, prefill still works, DFlash2 accept ~26%). NOT OOM/KV (pool huge headroom). Suspected spec-decode/DFlash2 or CUDA-graph interaction at high ctx relative to window.
- Root cause NOT yet determined (Victor wants investigation).
- 480K/seq12 NOT cleanly better than 1M/seq64 for the 400K agent goal due to the high-ctx stall.


## ROOT CAUSE (found 2026-09-05)
The 480K decode stall past ~288K = **Triton/TileLang kernel JIT compilation during live inference**.
vLLM log (jit_monitor.py): "Triton kernel JIT compilation during inference: <kernel>. This causes a latency spike; consider extending warmup to cover this shape/config."
6 kernels JIT'd mid-run on the 480K boot:
  BuildPrefillChunkMetadataKernel, _resample_kernel, _rejection_kernel,
  _prepare_dflash_inputs_kernel, mhc_pre_big_fuse_with_norm_tilelang, _compute_local_logits_stats_kernel

Mechanism: as growing context crosses chunk/spec-decode shapes NOT covered by boot warmup, vLLM
pauses decode to JIT-compile the exact kernel -> 0-0.6 tok/s stalls. 1M lane's boot warmup covered
more of these shapes; fresh 480K boot did not fully warm high-context shapes.

NOT seq12, NOT OOM/KV (pool has ~3x headroom; 34% worst-case). It is COLD KERNEL COMPILATION.

Fix: extend boot warmup to cover the workload's actual shapes (large-prefill + DFlash2 past ~288K)
so kernels compile at boot, not during inference. vLLM's own jit_monitor recommendation.


## FIX CONFIRMED (2026-09-05) — warmup eliminates the stall
After the stalling kernels had JIT'd once (from earlier probe runs), the SAME C1
growing-context probe on the 480K lane runs FLAT-FAST with NO stall:

WARMED lane (kernels compiled), C1 growing 32K->416K:
  every turn: 2.9-5.8s (total 51s)
  past 288K (previously stalled 22-31s): NOW 2.9-4.3s

vs COLD boot (kernels JIT during inference):
  past 288K: 22-31s stall (total 173s)

=> The 480K decode stall was ENTIRELY a boot-warmup coverage gap. With kernels
warmed, 480K/seq12 is genuinely excellent: ~2.9-5.8s/turn growing 32K->416K, flat,
no stall. 480K config NOT flawed.

Fix to bake into boot: run a growing-context warmup sweep (glm_warmup.py, sweep
5K->400K) right after /v1/models ready, BEFORE serving real traffic, so the
chunked-prefill + spec-decode (DFlash2) + rejection kernels compile at boot.

Confirmed mechanism (matches vLLM jit_monitor): JIT during inference = latency spike.


## FULL CONFIRMATION — C3 warmed (3 agents, 32K->416K, 124s, NO stall)
- 3 distinct agents, thinking low, all grew to 416K.
- Turns ~7-11s/turn flat to 416K (vs cold-boot C3 which spiked 67-95s past ~192K).
- No decode collapse. Total 124s (clean).

## VERDICT
480K/seq12 is GENUINELY EXCELLENT once kernels are warmed:
- C1 warmed: 2.9-5.8s/turn flat 32K->416K (51s total vs 173s cold).
- C3 warmed: ~7-11s/turn flat to 416K (124s), no stall.
The earlier 288K+ stall was ENTIRELY a boot-warmup coverage gap, not a config flaw.

=> Fully-optimized NVFP4 recipe = 480K/seq12 + growing-context warmup sweep after boot
   (glm_warmup.py, 5K->400K). FP8 becomes an A/B, not a necessity.
